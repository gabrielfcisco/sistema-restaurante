# US-12 e US-13 — Painéis da cozinha e do bar

Base de implementação: branch sprint-02 do Felipe, commit eef72ad. Referências visuais preservadas em apps/cozinha/screenshots/image.png e apps/bar/screenshots/image.png.

## Entrega

- Uma interface compartilhada com três colunas: Recebidos, Em preparo e Prontos; filtro por status, contadores, observações, horário e tempo de espera.
- Cartões mostram quantidade, produto, mesa, comanda e pedido. A ordem é crescente por Pedido.dataHora, com desempate por pedido/item.
- Os dois aplicativos consomem o mesmo backend e banco. Cada rota fixa o setor no servidor; o cliente não define o setor por query ou corpo.
- Avanços RECEBIDO → EM_PREPARO → PRONTO → ENTREGUE, sem saltos ou retrocessos. ENTREGUE sai da fila e permanece no histórico.
- PATCH exige o status que o operador estava vendo. Em disputa, somente a primeira alteração é aplicada; a outra retorna conflito e a interface reconcilia o snapshot.
- O status geral do pedido usa o estágio menos avançado entre todos os itens, incluindo os do outro setor. Item e agregado são gravados na mesma transação.
- Filas recebem snapshots por SSE. O servidor verifica mudanças a cada 2 segundos enquanto há assinantes, inclusive itens gravados pela futura confirmação de pedidos da US-11. Alterações feitas por PATCH também solicitam atualização imediata.
- A interface refaz GET ao abrir/reconectar o SSE; um evento mais recente prevalece sobre GET antigo pendente. Em falha, conserva a última fila visível, avisa e pausa ações até reconectar.
- Sem login nos painéis, conforme decisão já registrada do Grupo 9. A API deve permanecer na rede interna. Nenhuma credencial da recepção ou da mesa é necessária.
- Comandas finalizadas/liberadas não oferecem itens acionáveis. Produto desativado não oculta um item de pedido já confirmado.

## Banco e compatibilidade

A nova migration 20261022000000_status_recebido acrescenta RECEBIDO ao enum existente e define esse default para novos pedidos/itens. Não altera as migrations anteriores nem reescreve status históricos.

Itens legados PENDENTE são apresentados e tratados como RECEBIDO no painel. A primeira transição os leva a EM_PREPARO. Imagens, cardápio e criação de pedidos não são implementados por estas histórias.

Antes de aplicar a migration, revisar DATABASE_URL e confirmar que é o banco de desenvolvimento esperado:

```sh
npm ci
npm run db:generate
npm run db:deploy
```

Nenhum banco do grupo é migrado automaticamente pelo aplicativo.

## Executar

Com a API e o banco de desenvolvimento disponíveis:

```sh
npm run dev:api
npm run dev:cozinha
npm run dev:bar
```

Sem arquivo de configuração, os painéis usam http://127.0.0.1:3333/api. Não precisam executar setup:sprint, que provisiona somente recepção/mesa.

Para outro servidor da rede interna, criar apps/cozinha/.desktop-config.json e/ou apps/bar/.desktop-config.json, ignorados pelo Git:

```json
{ "apiUrl": "http://192.168.1.50:3333/api" }
```

O bridge retorna somente a URL pública do painel e limita GET/PATCH ao seu setor. No empacotado, config.json fica no userData do aplicativo; RESTAURANTE_CONFIG pode indicar outro arquivo. Arquivo existente inválido gera erro de configuração, sem substituição silenciosa. HTTP é permitido para localhost e IPv4 privada nos painéis; as exigências de credenciais e HTTPS dos outros apps são preservadas.

Para testar no navegador com dev:ui, VITE_API_URL pode apontar à mesma API. Configurar CORS_ORIGINS para as origens utilizadas.

## Contrato de fila

GET /api/cozinha/itens e GET /api/bar/itens retornam ItemFilaDto[]. Cada linha contém idItem, idPedido, idComanda, idMesa, numeroMesa, nomeProduto, quantidade, observacao, setor, status e dataHora em ISO UTC. Não retornam CPF, telefone, nome do cliente, credenciais ou preço.

GET /api/cozinha/eventos e GET /api/bar/eventos abrem text/event-stream. Evento fila contém {"itens":[...]}, um snapshot completo e autoritativo, sem duplicar cartões. Evento indisponivel contém {} e interrompe ações até a próxima fila válida. Reconexão em 3 segundos e heartbeat em 15 segundos; proxies devem permitir streaming sem buffering.

PATCH /api/cozinha/itens/:idItem/status e PATCH /api/bar/itens/:idItem/status:

```json
{ "statusAtual": "RECEBIDO", "status": "EM_PREPARO" }
```

Retorno StatusItemDto com idItem, status e statusPedido. Item de outro setor retorna 404 ITEM_INEXISTENTE; concorrência retorna 409 ITEM_ALTERADO; salto/retrocesso retorna 409 TRANSICAO_INVALIDA. Cada aplicação em paralelo deve lidar com o conflito, sem repetir cegamente a ação.

## Verificações reproduzíveis

- npm run check: lint, tipos, testes HTTP/SSE/cliente e builds de todos os apps, além da validação do Prisma.
- RUN_MYSQL_TESTS=1 e TEST_DATABASE_URL habilitam testes reais contra servidor MySQL/MariaDB local. Cada teste cria um banco efêmero próprio e o remove ao terminar. Não aplica migrations ao banco citado na URL.
- Após npm run build, npm run test:operacao:desktop usa TEST_DATABASE_URL local para criar API e banco descartáveis. Abre janelas Electron ocultas e verifica separação de setores, filtros, preparo/entrega, reconexão automática, persistência e layout sem overflow. DESKTOP_SCREENSHOT_DIR opcional salva capturas.
- O teste desktop não cria pedidos no banco do grupo. Não precisa executar nem alterar os fluxos da recepção/mesa.
- O teste de integração conecta cozinha e bar por HTTP/SSE ao banco real e insere um novo pedido misto enquanto os dois streams estão abertos. Confere a distribuição por setor, a atualização por PATCH e a preservação do histórico sem duplicar itens.
- O GitHub Actions executa `npm run check` em Node 24 e MySQL 8 nos pull requests para `sprint-02`/`main`. As credenciais do serviço de banco são descartáveis e exclusivas do runner.

US-07 a US-11 continuam sob responsabilidade dos demais integrantes. Ao integrar a confirmação de pedidos, criar Pedido/ItemPedido na mesma API e usar RECEBIDO; as filas detectam automaticamente as novas linhas persistidas.
